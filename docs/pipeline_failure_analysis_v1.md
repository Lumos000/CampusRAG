# CampusRAG 流程与泛化失败原因分析

分析基于a44fed7源码、36题冻结运行日志、原始资料、模型输入重建及只读执行器探针。没有修改问答源码、重跑模型挑选答案或修改原评测分数。重建与探针记录见`data/eval/independent_v1/pipeline_diagnostics.json`。

## 分数差异的含义

12题开发回归与36题新题不是相同测试集，不能把100%到52.8%解释成同一批题发生能力退化。当前源码指纹与12题运行记录完全相同。此前开发集有3道校园题走专用快捷工具，另有1道校园面积题走通用计划；人工表格多数仅有2至3列，适合当时的示例构造规则。新题涉及多条款、否定与例外、正文上下限、无量纲绩点、6至7列表格和重复分类值，均未获得同等开发验证。

12题主要按最终Decimal数值与引用存在判分；36题还逐项复核问句要求、条件完整性和额外错误，另行检查引用。后者存在单助手评分局限，F02金标额外要求未询问背景也被单列。即使仅将F02核心回答算通过，总分也仅20/36，不能解释其余明确失败，尤其不能解释计算1/8。

此前将开发回归成功解释为通用能力基本补齐偏乐观。更准确的判断是：计算执行框架已实现，证据转为合法、语义正确计划的能力仍不足。模型权重未因本次开发被训练；这里的开发集适配偏差是提示、模板和测试结构层面的，不是参数训练过拟合。

## 实际调用链

原始问题先做显式年份解析，然后通过BM25、BGE、RRF及重排取得8条证据。服务用关键词区分数值题与普通文字题。

普通文字题直接拼接8条正文交给Qwen生成，没有经过逐条事实或否定条件核验；返回时把全部检索证据转换为引用。

数值题先尝试收费、师资和选科快捷工具。其余题只从表格候选构造Schema，并用正则把正文转成facts，最多提供4张表、每表3条示例、24条facts。原始正文并不会作为数值计划的另一份完整上下文继续提供。模型根据运算提示和自动示例生成计划，Python检查并最多共享一次修复机会，然后执行完整SQLite筛选与Decimal运算。成功结果由模板直接输出，失败则拒答。

因此“检索正确”“Schema真实”“JSON能解析”和“实际问题被正确理解”是不同环节，任何一个都不能替代下一环节。

## 数据入库与上下文边界

数据库完整性、外键、token上限及规范化元数据通过，不代表表头、条款归属等语义已经正确。

- 转专业L01的第1条证据主体是第九条的可放宽情形，末尾才出现“第十条……不得申请转专业”；真正的五类禁止情形在第2条证据。这种跨块边界把新条款标题接在上一条款正文后，容易使小模型错配。记录的heading_path仍为“第一章 总则”，服务拼接时又不提供该字段。
- 贷款指南表432的字段名称是“毕业当年（即2029年）”“12月20日”“偿还本年度……111天……”，即数据记录被当作了Schema表头。这不是本题比较额度所需的表，却进入了计划候选。
- 课程对照表53和课程安排表381同为Sheet1，同属2026-2027学年，但业务意义不同：前者254条课程代码对应记录，后者116条开课安排。现有年份与标题子串不足以确认具体统计对象。

这些问题说明需要抽查字段角色、条款边界与表的业务描述，而不是继续只增加资料数量。

## 检索召回足够但上下文不纯

本集32道可回答题的必要证据入口均出现在默认前8条，因此“完全没查到资料”不是主要失败原因。这个指标不能证明8条内容都相关或排序、粒度理想。

普通文字题8条证据原样拼接，没有按条款、对象和版本重新组织。P04同时看到首贷、续贷、更换共同借款人、共同借款人资格等段落，最后把不同场景的到场人和材料混用。F06甚至第1条证据就含“不附带任何条件”，仍生成“可附带条件”，这是明确的生成理解错误，不能全部归因于检索噪声。

重建普通回答提示约161至3054个Qwen token，平均约1926个，未发现超出配置7168或模型上下文长度的证据。配置本身尚未实际用于输入限长，但不能将本次错误解释为已发生上下文溢出。候选的语义混杂比绝对长度更值得优先处理。重排在本集也未显示稳定收益，但没有“删掉重排就会提高答案准确率”的端到端对照证据。

## 正文变成facts时丢掉了核心数值

`NumericEngine.text_facts`主要识别“标签 + 为/有/是/冒号 + 数字 + 指定单位”。它不是通用事实抽取器。

| 题目 | 检索原文 | 实际传给数值规划器的facts | 结果 |
|---|---|---|---|
| C01最低时薪 | 不低于每小时24元 | 无 | 未调用模型规划即拒答 |
| C02工时余量 | 每周不超过8小时、每月不超过40小时 | 只有无关满意度0.9132 | 规划无所需操作数，复制甲库/乙库示例 |
| C03贷款额度差 | 本专科上限20000元、研究生上限25000元 | 只有“年申请一笔期限17年” | 误用还款示例表和字段 |
| C04绩点差 | 1.8及以上、1.5及以上 | 无 | 未调用模型规划即拒答 |

正则也直接在带换行的PDF文本上匹配，缺少标签跨行、限定词、复合单位和无量纲类型支持。下限、上限、基准、实际值的语义应保留，不能简单放宽成抓取附近任意数字。仅扩大模型或JSON算子不会补回被表示层丢弃的证据。

## 自动提示示例在复杂Schema上产生错误引导

`step_example`默认使用第一张候选表、首个文本字段和首个数值字段。没有可用数值字段或仅有正文facts时，仍保留表7、字段71/72和甲库/乙库示例。

课程表53中首个数字列是“序号”，首个文本列是“学院”，真正需要筛选的是“慕课名称”。C07的实际自动示例为：对序号求和，学院in[管理学院,管理学院,管理学院]。

原因还有两层：`_object_key`删除“学院”等后缀，把“管理学院”变为“管理”；而“管理”出现在问题的“战略管理”中，于是被当成用户提到的对象。示例标签来自3条同学院记录，又没有去重。模型最后确实产生了学院条件、重复管理学院及文字列sum。C08同样选择了另一张课程安排表并沿用这类筛选。

这不是单纯“小模型没有遵守提示”。提示中被称作按真实Schema构造的示例，本身已经带入错误的字段角色和实体关系。在2至3列人工小表上，第一文本列常恰好是对象名称，因此开发回归没有暴露该假设。

## 运算提示仍是表层词匹配

`operation_hint`遇到“平均”就优先提示average。C04中的“平均学分绩点”是字段名称，问题真正要求的是两项门槛相减。该题实际先在facts抽取处停止，所以错误hint不是本轮拒答的直接原因；但只修抽取，后续仍会收到错误运算引导。

“记录合计多少条”可能需要count，不应因为“合计”而提示对序号sum；多步问题的最终运算也不等于完整步骤。提示应帮助模型理解计量对象与操作，而不是用一个关键词替代语义判断。

## 执行器能计算，但部分校验边界不适合分类聚合

只读探针使用人工明确的正确计划，不调用模型、不计入正式分数，结果如下：

| 隔离验证 | 执行结果 |
|---|---|
| C06按慕课名称eq计数 | 成功，10项 |
| C07按慕课名称in筛选后count | 失败，称光纤通信重复，repairable=false |
| C07两个eq分别count再add | 成功，6项 |
| C08两个eq计数、相加、整表计数、ratio | 成功，2.3622047244…% |

问题在于in被定义成“每个值只能匹配一行”。对于唯一对象查找可合理限制，但“光纤通信”本来对应3个校内课程代码，重复分类标签是合法数据，不是歧义。相同统计范围换一种等价计划就能执行，证明不是SQLite或Decimal不会计算。

此外，小时常数不在`_step_input`允许单位中。即使C01抽取出时薪，直接提供{literal:12,unit:小时}也会被拒绝。这是对修复路径的额外限制，不是C01本轮最先触发的失败原因。

不能因此删除字段、单位、年份或完整性校验。需要区分唯一lookup、允许多行的分类filter/聚合，以及真正重复或冲突的记录。

## 修复机会与错误解释

一次修复没有根本问题，问题是上下文和错误分类：模型仍面对同一个不适配示例；重复分类被ValueError判作不可修复数据问题；有的错误只说明ID不在表中，未说明应使用哪类字段。C06最后计划只有约57个token，明显未达到1024输出预算，不能凭JSON不完整就判断是长度截断。

日志只保存last_raw及最后一个计划，没有完整保留首轮和修复轮，因此不能精确区分每题首次失败与修复失败的贡献。R04最终把field_id错误直接传给用户，虽没有猜利息，仍没有解释个人计算缺少哪些参数。

## 普通文字分支缺少相应核验

数值成功后使用程序模板；普通文字则直接采用模型草稿。F06反转捐赠限制，L01把可放宽条件当作禁止条件，P04混用办理情形，L04编造法定假日。没有后置的条款号、适用对象、否定条件及额外事实核对，也没有简短摘录回退。

`ANSWER_PROMPT`将输入统称“经过系统验证的证据”，实际上这些只是来源与检索候选，不代表其中每个事实都经语义验证。引用生成只按文档去重，服务将全部检索证据传入，既未证明模型实际用了这些片段，也未证明回答中的结论被支持。故“有官方来源”和“回答内容正确”必须分开。

## 为什么自动测试仍然通过

多数执行器测试直接提供正确计划或FakeGenerator，能证明算子、来源管理和安全边界满足断言，不能证明0.6B会对真实多列表和复杂条款生成正确计划。开发回归的结构较简单且已参与提示调试；78项代码测试并不构成78道真实模型问答题。

## 改进顺序

1. 先修“证据到表示”：按条款保留标题和适用范围；补正文上下限、每单位值及无量纲数值，保留原文、限定词和口径。别先增加数据量。
2. 修示例生成：没有真实可绑定字段时不放入虚构表ID；不按列位置决定语义；序号不能当度量、学院不能代替课程名称；正文通道使用facts示例。
3. 修计划与校验接口：区分count/sum和字段类型，区分分类多行与唯一lookup；错误反馈给出可用字段和预期类型，不增加无上限重试。
4. 收紧普通回答：先定位问题要求的具体条款，简洁引用必要原句，核对否定及条件，减少无关扩写；仅列支撑实际结论的引用。
5. 将v1转成开发回归集，另建未见v2检验。若要判断某次代码修改是否造成真实退化，须对旧版和新版运行同一组题，而不是比较12题和36题两个百分比。

现有检索、数据库与Decimal执行主体可以保留。优先修复的是各模块交界处的语义丢失、错误提示示例和不合适的约束，不需要通过增加多Agent、大模型或复杂框架掩盖这些问题。
